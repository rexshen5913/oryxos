# 核心階段的範圍與驗收邊界

四份規劃文檔把「4 週、每週 3 小時、合計 12 小時」寫成核心階段的時間約束，同時要求該階段交付 8 個 package、11 個 CLI 命令、10 個 REST 端點、五個內建 Tool、MCP Client、SQLite 三張表，並要求「每個功能模組至少有一個端到端測試」——而憲法第四條的嚴格 TDD 不可協商。這在算術上不成立：光是性能驗收要求的「單節點 10 個 Agent 穩定運行 4 小時」，掛機時間就佔滿整份預算的三分之一，且超過任何單週的 3 小時配額。現決定**讓時間讓步**：12 小時降級為節奏參考，不作為驗收條件；範圍照需求文檔第 5 章保留。連帶確立三條範圍邊界如下。

## Considered Options

考慮過另外兩個方向，都拒絕了：

- **讓範圍讓步**（保住 12 小時，砍到只剩 Demo 一＋二）。代價是核心階段沒有 Web Service，而四份文檔反覆論證 Web Service 是「OryxOS 區別於 OpenClaw、Hermes 的關鍵能力」。砍掉它，剩下的東西跟一個個人 Agent runtime 沒有區別，核心階段就失去定位意義。
- **讓驗收門檻讓步**（範圍與時間都留，砍測試強度）。這要修訂憲法第四條「測試先行鐵律——不可協商」。為了一個沒有推導過程的數字去改最硬的鐵律，是拿最硬的東西換最軟的東西。

決定性的證據是需求文檔第 12 章自己已經寫明：「如果某一週完不成，立刻把當週末段功能挪到擴展功能」。文檔本來就預設範圍會滑動，12 小時從來不是約束，而是估算——且是四份文檔裡唯一沒有任何推導過程的數字。

## 連帶確立的三條邊界

**一、性能驗收移出核心階段 AC。** 需求文檔第 13 章自述性能指標「不達標不影響發布」——一條不影響發布的條件，定義上就不是 acceptance criterion。這些指標改列為擴展階段的優化目標。核心階段的硬條件只有第 13 章那五個 demo。

**二、砍掉 `oryxos gateway`，核心階段 11 個 CLI 命令。** 核心階段唯一的 Channel 是 CLI，而 CliChannel 是「讀 stdin 寫 stdout」的互動式實作，守護進程模式下無 stdin 可讀，因此 gateway 實際只掛得起 Web Service，**等同 `oryxos server` 的別名**。憲法 3.1（YAGNI）與 3.2（反過度工程）都指向砍掉。等擴展階段真有 Slack／Telegram 等多 Channel 時，gateway 才有它該有的語義。

**三、區分「快速開始」與「部署運維手冊」。** 需求文檔第 13 章要求「完整的部署文檔」作為驗收，第 7 章卻把「部署運維手冊」列為社區共建——發布條件依賴一份被本階段排除的產物。拆開後矛盾消失：**快速開始**（從 `git clone` 到 `oryxos chat` 跑通）核心階段必交，已由第 5.13 節的專案主頁承擔；**部署運維手冊**（生產部署、K8s、監控、故障排除）留社區共建，且核心階段本就**不該**交付它——第 12 章自述「核心階段不建議在生產環境跑高敏感場景」，此時給出生產部署手冊等於誤導使用者。

## Consequences

核心階段的發布硬條件收斂為兩項：第 13 章五個 demo 全部跑通；快速開始可複跑。後者取代原本不可驗證的「新手 30 分鐘內完成單節點部署」，改為**在乾淨環境依快速開始的步驟，能從 `git clone` 走到 `oryxos chat` 成功對話一輪**——步驟可數、結果二元、任何人可複跑。

「4 週」仍可作為節奏參考保留在里程碑章節，但不得再出現在驗收章節，也不得被引用為砍功能的理由——要砍功能請援引 YAGNI，不要援引時間。
