## 一、什麼是 Agent OS

### 1.1 一個明確的定義

Agent OS 是執行和管理 AI Agent 的底座系統。它裝在使用者（或企業）自己的機器上，向上為各類 Agent（運維助手、客服助手、HR 助手、銷售助手等）提供統一的執行環境，向下接入模型、渠道、工具、記憶、身份和審計基礎設施。

一個合格的 Agent OS 必須具備五件事。

- **Agent 配置和生命週期管理。** 能註冊、啟動、監控、銷毀多個 Agent，每個 Agent 有獨立的 prompt、模型、工具、渠道、記憶。Agent 在底座上配置出來，不是寫程式碼寫出來的。
- **統一對外接入。** IM（Slack、Telegram、Discord 等）、郵件、Web、HTTP API，所有 Agent 共用一套對外接入層。（業界泛述；OryxOS 專屬術語把訊息渠道 Channel 與 Web Service 分開，見需求文檔）
- **統一對內系統接入。** LLM Provider、工具（MCP 或外掛）、企業 IT 系統、知識庫，所有 Agent 共享一套接入層。
- **統一記憶。** 跨 Session 的長期記憶、可復用的 Skill 模板、跨 Agent 的知識沉澱。
- **Tool 呼叫和沙箱執行。** Agent 通過 LLM Function Calling 呼叫 Tool，Tool 在沙箱裡執行，保證安全邊界。

> **💡 核心觀點：** 這裡要把一個容易混的詞辨清楚：Agent OS 跟 agent runtime（Agent 執行時）不是一回事。

agent runtime 指的是讓單個 agent 跑起來的執行核心，負責 LLM 呼叫、工具執行、上下文管理、迴圈控制，上面五件事裡的第五件大致屬於這一層。Agent OS 的核心確實包含一個 agent runtime，但它在 runtime 之上還要管前四件事：多個 Agent 的生命週期、統一的對外對內接入、統一記憶、以及後面會講的多租戶和審計。

借作業系統的類比說，runtime 像是單個程序的執行環境，Agent OS 像是管理一群程序、排程資源、提供共享服務和治理的那層。一句話，runtime 讓一個 agent 跑起來，Agent OS 讓一群 agent 在企業裡被管起來。

一句話：Agent OS 解決的是"使用者要同時跑 N 個 Agent 時，這些 Agent 共享的基礎設施層應該長什麼樣"。

### 1.2 Agent OS 長什麼樣

部署形態是這樣：

- 使用者部署一個 Agent OS 實例（單一服務），裝在自己的機器、伺服器或 K8s 上。
- Agent OS 自帶 Web 管理台或 CLI 工具。
- 使用者通過 Web 或 CLI 在 Agent OS 上建立 Agent（上傳或者往某個目錄存放一段程式碼）、註冊 Tool 和 Skill、配置渠道。
- Agent 跑起來後，最終使用者通過 IM 或 Web 跟 Agent 對話。
- Agent OS 允許自動執行 Agent。

業務方關心的事很簡單：

- 寫一個 Tool 實現某個具體功能（可以用任何語言）
- 然後在 Agent OS 上配置一個 Agent 把這個 Tool 用起來。

業務方不需要寫 Agent 後端程式碼，Agent 是配置出來的，不是寫出來的。業務方不感知訊息從哪來、LLM 怎麼呼叫、使用者身份怎麼管、審計怎麼落、上下文怎麼續，這些都是 Agent OS 的事。

### 1.3 Agent OS 跟相鄰概念的區別

這件事容易混淆，需要專門講一下邊界。

把 Agent OS 跟最容易混的三類東西擺在一起看，區別就清楚了。

| | 產物 | 誰來用 | 部署形態 | 跟 Agent OS 的關係 |
| --- | --- | --- | --- | --- |
| 編排平台（Dify、Coze、扣子） | 一條 workflow | 業務人員、開發者 | 多為 SaaS 或自部署平台 | 可跑在 Agent OS 之上，拿它當後端 |
| 框架（LangChain、langchaingo、Eino） | 程式碼 | 開發者 | 自己搭執行環境 | 可作為 Agent OS 的底層元件 |
| 大廠中台 / SaaS（Glean、Bedrock AgentCore、Agentforce） | 完整應用 | 企業採購方 | SaaS，綁雲生態 | 不同象限，不可私有部署 |
| Agent OS（本文主題） | 配置出來的常駐 Agent | 企業 IT、業務方 | 裝在自己機器上的執行時 | 它自己 |

編排平台是 visual workflow builder，業務人員或開發者用拖拽方式把節點拼成一個 workflow，平台負責執行。它的產物是流程，適合做複雜業務流程編排；Agent OS 的產物是配置出來的、常駐服務的 Agent。兩者層級不同，編排平台可以跑在 Agent OS 之上，把 Agent OS 當後端。

框架是一組庫或 SDK，給開發者用程式碼寫 Agent，產物是程式碼，執行環境要開發者自己搞定；Agent OS 的產物是一個裝好就跑的服務，基礎設施一應俱全。框架可以作為 Agent OS 的底層元件，比如 Agent OS 內部用 go-openai 實現 LLM 呼叫。

大廠中台和 SaaS 產品是完整應用，綁各自的雲生態或協作平台，產品形態是 SaaS，不是裝在使用者自己機器上的執行時。Agent OS 是開源、可私有部署的底座，不鎖生態。

這三個邊界劃清楚之後，Agent OS 在整個生態裡的位置就清楚了。

## 二、業界兩個最具代表性的開源 Agent

業界做開源 Agent 這件事，目前最具代表性的是兩個專案：OpenClaw 和 Hermes Agent。這兩個專案的具體架構、社群和安全細節，已經有專門的文章詳細拆解過，這裡不再展開，只從業界調研、Agent OS 格局的角度，把它們各自代表的取向和合起來呈現的格局講清楚。

### 2.1 OpenClaw 和 Hermes Agent

OpenClaw 由 PSPDFKit 創始人 Peter Steinberger 在 2025 年 11 月發布，Node.js 實現，MIT 協議。它代表的是消費者級、開發者優先的取向：二十多個渠道、上萬個社群 skill、極強的可玩性，到 2026 年 4 月突破 30 萬 GitHub stars，是 GitHub 歷史上增速最快的開源專案。它的強項是社群活力和能力豐富度，軟肋是企業級安全和治理，CVE、惡意 skill、憑證收割等結構性問題反覆出現，企業部署要靠 Tank OS 這類二次加固才能勉強上生產。一句話，OpenClaw 是個人和小團隊的 Agent OS。

Hermes Agent 由開源 AI 實驗室 NousResearch 在 2026 年 2 月發布，Python 實現，MIT 協議。它代表的是工程級、健壯性優先的取向：三層記憶、自我進化的 skill 機制、安全掃描、HERMES_HOME 多使用者隔離，企業級方向投入明顯，有商業化樣本和雲廠商背書，到 2026 年 5 月約 15 萬 stars，且在日活推理量上一度反超 OpenClaw。它比 OpenClaw 更接近企業，但企業級 OS 治理（多租戶 RBAC、SSO、完整審計）仍是空白。一句話，Hermes 是更偏團隊和企業的 Agent OS。

兩個專案合起來，基本就勾勒出了當前開源 Agent OS 的格局：一個偏消費級可玩、一個偏工程級健壯，都從個人和小團隊起步，產品形態都是"裝在自己機器上、提供完整 Agent 執行環境的底座"。這個格局的意義不在於它們各自做了什麼，而在於它們合起來留下了什麼空白，而那個空白正是理解 OryxOS 定位的起點。

### 2.2 兩者共同留下的空白

落到空白上，開源 Agent OS 領域有幾個真正沒被填的位置。

- **第一，完整的企業級治理。** OpenClaw 和 Hermes 都偏個人到小團隊定位，真正企業級的多租戶 RBAC、SSO 接入、審計架構、合規留證還是空白。PTG 和 Tank OS 這種二次加固方案存在，但它們是補丁，不是 day one 設計。
- **第二，企業 IT 系統的深度整合。** 兩個專案對企業 IM 渠道（Slack、Discord 等）都通過社群擴展支援，但企業現有 IT 系統（ERP、CRM、CMDB、監控系統）的深度對接還是空白，需要每家自己寫適配。
- **第三，基礎設施母語 Go 的缺位。** OpenClaw 是 Node.js，Hermes 是 Python。而寫遍了所有雲基礎設施的 Go，沒有任何一個專案把"Agent OS"作為定位。這一點後面單獨講，因為它對企業市場尤其重要。

## 三、企業為什麼需要一個私有可控的 Agent 底座

這一章是整份調研論證的重心。這裡要把一個判斷講清楚：企業真正的剛需，不是"Agent OS 這個品類"，而是"一個私有、可控、可審計的 Agent 統一底座"。這兩者聽起來像，但錨點完全不同。前者是一個可能演變的概念，後者是一個不會變的需求。

### 3.1 大盤需求是真實的

業界對企業 AI Agent 的需求已經形成共識。Anthropic 2026 State of AI Agents 報告調研 500 多位技術領導者，超過半數已經部署多步驟 agent workflow，絕大多數計劃在 2026 擴展更複雜的用例，多數報告 AI Agent 投資帶來可衡量的經濟回報。需求側沒有懸念。

### 3.2 但真正的難點不在"做出一個 Agent"，在"讓它在企業裡可控地跑起來"

同一批資料裡有一個反差：大量 agent pilot 永遠到不了 production，相當比例的 enterprise pilot 無法 scale。資料矛盾的背後是同一件事。單個 Agent 容易做出 demo，但一旦要做成企業級、跑在生產環境、服務全公司，就立刻撞上一堆工程問題。

Anthropic 報告裡最硬的資料指向的正是這些工程問題：企業認為最大的挑戰是整合、是資料訪問質量、是實施成本、是變更管理。安全治理上，多數組織在過去一年報告過 AI agent 安全事件，而只有很小比例的組織在 agent 進入生產時有完整的 IT/security approval。Tool calling 在生產環境有不低的失敗率，且多數是靜默失敗。

這些問題，沒有一個是"模型不夠強"能解決的，全都是"底座不夠穩、不夠可控"的問題。

### 3.3 嚴監管企業的剛需是確定的、不會變的

把鏡頭對準最硬的那批客戶，也就是銀行、政府、電信、能源、醫療。這些嚴監管企業有幾條鐵律：

- 核心業務的資料不能出企業
- 系統必須完全可審計
- 任何新元件都要過現有的安全和合規流程
- 要能納入現有的運維與平台體系（雲原生 / K8s），並透過中立協議對接既有系統。

在這幾條鐵律下，他們的選擇被極大地收窄了。他們不會把核心業務的 Agent 跑在 SaaS 上（資料出企業），不會跑在綁定某個公有雲的產品上（鎖生態），也很難直接把一個有 CVE 和憑證收割史、預設權限寬鬆的 Node.js 開源專案放進生產（過不了安全審查）。他們需要的是一個私有部署、完全可審計、能納入現有 IT 治理、跟現有雲原生 / K8s 平台對齊、並透過 MCP / HTTP / gRPC 中立協議對接任何既有系統（不預設企業是哪種語言的技術棧）的 Agent 底座。

這個需求是確定的、剛性的、且當前無人滿足的。

> **💡 核心觀點：** 而且關鍵在於：無論"Agent OS"這個詞將來流行不流行、這個中間層最後是獨立存在還是被某一層吸收，"嚴監管企業要一個自己能完全掌控的 Agent 底座"這件事都不會變。

這是一個錨在企業本質約束上的需求，不是錨在一個技術概念上的需求。

### 3.4 價值錨點

這個私有可控的底座，對企業的價值是具體的：直接降本、直接增效、跨系統協同、合規與審計可落地、讓普通員工也能用上 AI 能力。

而最深的一個價值錨點是知識沉澱。通過 Skill 體系，把高級員工的經驗資產化、留在企業，新員工可以繼承。沉澱的知識、經驗、AI 能力，永遠留在企業，這是私有底座區別於 SaaS 的根本價值。

## 四、基礎設施母語的缺位：Go 在這件事上的位置

### 4.1 Go 的 AI 工程現狀：有函式庫，沒有底座

Go 在 AI 工程領域已經有東西，但沒有任何一個是 Agent OS 這一層的底座。

go-openai（社群維護、事實上的標準客戶端）解決 LLM 呼叫，覆蓋 OpenAI 兼容協議，而 OpenAI 兼容協議如今已是主流模型對外暴露的通用格式，接一家等於接一批。CloudWeGo 的 Eino、以及 langchaingo 這類框架，把 Chain、Agent、RAG 這些能力補了上來，是 Go 版的 LLM 應用開發框架。官方 Go MCP SDK 與社群成熟實作（如 mark3labs/mcp-go）則把工具接入這一層做扎實。

這些都是庫或框架，產物是程式碼、需要開發者自己搞定執行環境。用 Go 寫的、裝好就跑的 Agent OS 底座，在業界幾乎為零。OpenClaw 是 Node.js，Hermes 是 Python，Go 生態在 Agent OS 這個層級是一塊明顯的缺位。

### 4.2 為什麼這個缺位值得補：底座該用基礎設施母語

這裡換一個角度看"Go 沒人做 Agent OS"這件事。它不是從"哪種語言的人更多"這種角度，而是從"這一層本質上是什麼、該用什麼寫"的角度。

先把 Agent OS 的本質看清楚。它要當企業內多個 Agent 共享的常駐底座，管生命週期、管接入、管記憶、管隔離、管審計——這些沒有一件是應用層的活，全是典型的基礎設施職責。Agent OS 本質上就是一層基礎設施。

而過去十年，雲原生基礎設施幾乎清一色是 Go 寫的：Kubernetes、Docker、containerd、Prometheus、etcd、Consul、Terraform、NATS。要挑一門語言來寫一層新的、要跑在這套雲原生地基上的基礎設施，Go 是它的母語，是本命，不是勉強。用基礎設施的母語寫基礎設施，接縫最少。

反過來看業界現狀，就有一層反諷：Node 有 OpenClaw、Python 有 Hermes，各自的生態都長出了自己的 Agent OS；唯獨寫遍了所有雲基礎設施的 Go，還沒有任何一個專案把"Agent OS"當定位。基礎設施的母語，偏偏在"Agent 基礎設施"這一層缺席了。這道缺位處，今天要靠跨生態的膠水去填——一個雲原生體系的企業想要一個私有可控的 Agent 底座，只能去用 Node.js 的 OpenClaw 或 Python 的 Hermes，然後在兩套技術棧的接縫處寫大量膠水，去對接自己的 K8s 平台、復用自己那套 Prometheus / OTel 運維鏈、走自己的審計流程。而膠水是脆的、是成本。

補上這個缺位，讓 Agent OS 這一層也有一個用基礎設施母語寫的、跟整套雲原生基礎設施咬合的實現，是一件讓生態變完整的事。不是因為 Go 比別的語言強，而是因為一層基礎設施，本就該用寫基礎設施的那門語言來寫。

### 4.3 Go 做這件事的六個具體支點

這個缺位之所以現在值得、也能夠被 Go 補上，有六個具體的支點。

- **一、基礎設施母語。** Agent OS 是底座，而 CNCF 版圖——K8s、Docker、Prometheus、etcd、Consul、Terraform、NATS——幾乎清一色是 Go 寫的。用母語寫一層新的底座，跟現有雲原生基礎設施咬合得最緊，這是最根本的一條。
- **二、裝好就跑是預設。** 單一靜態二進制、約 10ms 級啟動、低記憶體佔用，是 Go 的 day-one 預設，`CGO_ENABLED=0` 靜態編譯即得，零 caveat。"像裝一個服務一樣自然"這句話，Go 直接就能兌現。
- **三、併發本命。** Agent OS 的典型負載是"大量並發 Session、每個都卡在 LLM 的網路 IO 上"，這正是 goroutine 的本命場景。輕量協程加 `context.Context` 做取消、超時、追蹤傳遞，原生且成熟。
- **四、MCP 一等公民。** Tool 生態通過 MCP 接入，而 Go 有官方 MCP SDK，加上社群成熟實作（如 mark3labs/mcp-go）。工具接入這一層，在別的語言版本裡是要擔心成熟度的風險項，在 Go 這裡直接翻轉成強項。
- **五、運維面對齊 K8s。** 對一個要跑在 K8s 上的底座來說，運維面對齊比語言對齊更要緊。Prometheus 的 client_golang 就是其參考實現，log/slog 是標準庫的結構化日誌，OTel、Operator 也都是 Go 的主場。指標、日誌、追蹤、生命週期管理，全都跟企業現有的雲原生運維體系無縫。
- **六、顯式優於魔法。** Go 沒有反射裝配、動態代理這類框架魔法要搏鬥，Provider、Tool 一律顯式註冊。這恰好對齊 OryxOS"自己實現 ReAct 迴圈、完全可控"的既有哲學——底座的每一條執行路徑都看得見、可審計，而不是藏在框架的自動裝配背後。

### 4.4 Go AI 工程生態的成熟是先行信號

Go 的 AI 工程生態正在快速成熟，這件事本身就是一個先行信號。go-openai 已經成為 Go 接 LLM 的事實標準客戶端，OpenAI 兼容協議讓"接一家等於接一批"成立；CloudWeGo 的 Eino、langchaingo 這類框架相繼出現，把 Chain、Agent、RAG 這些應用開發能力補齊；官方 Go MCP SDK 的落地，則把工具接入這一層做扎實。

這條軌跡跟當年 LLM 呼叫層被補上是同一個邏輯：底層能力先就位，上面那一層"Agent OS"自然成為下一個要被補的位置。Go AI 工程的基礎設施層正在 2025 到 2026 這段時間成形，順著技術棧演化的邏輯順序，它會走向 Agent OS 這一層級。缺的，正是站在這套地基上、用基礎設施母語寫的那個底座。

## 五、OryxOS 的定位與願景

前面把 Agent OS 是什麼、業界做到哪、基礎設施母語 Go 缺在哪都講清楚了。這一章講 OryxOS 自己想做什麼、想做成什麼樣子。

### 5.1 OryxOS 是什麼

OryxOS 是一個企業能完全掌控的、雲原生原生的、私有可審計的 Agent 統一底座。

它裝在企業自己的 K8s、伺服器或物理機上，作為統一底座，在底座上跑各種業務 Agent（運維助手、客服助手、HR 助手、銷售助手、知識管理助手等），共享一套渠道接入、模型路由、記憶系統、工具呼叫、安全審計能力。資料完全留在企業自己的基礎設施，不鎖任何雲生態。

業務方在 OryxOS 上配置 Agent（prompt、模型、Tool 列表、渠道綁定），Agent 跑起來；業務方寫 Tool（用 Go、Python、Shell 或任何語言，通過 MCP 協議暴露）接入 OryxOS，Agent 就能用上。業務方不需要寫 Agent 後端程式碼，只需要寫 Tool 實現和 Skill 配置。

### 5.2 OryxOS 把自己錨在哪裡

這是 OryxOS 定位上最要緊的一個選擇，呼應第一章和第三章的判斷。

OryxOS 用"Agent OS"這個框架來理解和構建自己，因為這個框架好用，五件事講得清楚，作業系統的類比幫助思考。但 OryxOS 不把自己錨在"Agent OS 這個概念"上，而是錨在它背後那個不會變的企業剛需上：嚴監管企業需要一個自己能完全掌控的 Agent 底座，私有部署、完全可審計、跟現有雲原生 / K8s 平台對齊、資料不出企業、IT 能掌控。

這個區別很重要。錨在概念上，意味著如果有一天"Agent OS"這個詞被別的說法取代、這個中間層被上下層吸收，專案就失去了立足點。錨在需求上，意味著無論技術概念怎麼演變，OryxOS 服務的那個需求都還在。嚴監管企業要私有可控、要跟現有雲原生 / K8s 平台對齊，這件事不會因為一個詞的流行與否而改變。

> **💡 核心觀點：** OryxOS 把根扎在不變的東西上。

### 5.3 OryxOS 的願景

OryxOS 想做成的樣子，可以用幾個畫面來描述。

- 讓企業裝一個 Agent 底座，像裝一個雲原生服務一樣自然（單一二進制，裝上就跑）。不需要學新的技術棧，不需要為它單獨搭運維和審計，裝上就納入企業現有的體系。
- 讓業務方只關心業務。渠道、模型、記憶、多租戶、審計這些公共能力下沉到 OryxOS，業務方之上只寫 Tool、配 Agent，上一個新 Agent 不用重複造這些輪子。
- 讓資料和能力都留在企業。模型可以接外部 API，也可以用本地 Ollama 或 vLLM，但資料完全留在企業自己的基礎設施，OryxOS 本身不收集任何企業資料。更進一步，通過 Skill 體系讓高級員工的經驗沉澱下來、資產化、留在企業，新員工可以繼承。沉澱的知識和能力，永遠屬於企業。

把這幾個畫面收成四個詞：統一、私有、易接入、可觀測。

- **統一** 是企業內多個 Agent 共享一套底座；
- **私有** 是資料和部署完全在企業自己手裡；
- **易接入** 是基於標準 Go 工程結構、透過 MCP / HTTP / gRPC 中立協議對接任何既有系統（不預設企業是哪種語言的技術棧）、Tool 用 MCP 任何語言都能寫；
- **可觀測** 是標準 Prometheus 指標、結構化日誌、健康檢查、Web 管理台，適配企業現有監控告警。

### 5.4 OryxOS 的邊界：做執行時，不做編排

OryxOS 的定位有一條清晰的邊界：在分層上守住執行時這一層，不往上做編排。這裡的"執行時層"是順著第一章的區分說的，指 OryxOS 站在編排平台和應用之下、做承載 Agent 跑起來的底座，而不是說 OryxOS 縮成了一個只管單 agent 執行的純 runtime。它仍然是完整的 Agent OS，多 Agent 管理、多租戶、審計這些 OS 級能力都在，只是相對編排平台而言，它的位置在下面那一層。

OryxOS 做的事是提供 Agent 執行所需的基礎設施，包括 Channel、LLM Provider、Memory、Tool 註冊、Sandbox、多租戶、SSO、審計、可觀測性、Web 管理台。業務方在上面配置 Agent，Agent 跑起來。

OryxOS 不做可視化 workflow 編排、複雜任務分解、多 Agent 顯式協作。如果業務需要複雜 workflow，可以用 Dify 之類的編排平台在 OryxOS 之上跑（Dify 作為客戶端呼叫 OryxOS 的 API）。OryxOS 跟編排平台是互補關係，不是競爭關係。這條邊界讓 OryxOS 專注做好"底座"這一件事。

### 5.5 OryxOS 不是什麼：跟 Dify 工作流和 LangChain 框架的區別

第一章已經從概念上劃過 Agent OS 跟相鄰概念的邊界，這裡站在 OryxOS 的角度再正面講一遍，因為這是最容易被問到、也最容易混淆的地方。把 OryxOS、Dify 這類編排平台、LangChain/langchaingo 這類框架放在一起，用三個維度看，區別就清楚了：產物是什麼、誰來用、跑在哪一層。

| | 框架（LangChain、langchaingo） | 編排平台（Dify、Coze） | OryxOS |
| --- | --- | --- | --- |
| 產物 | 程式碼 | 一條 workflow | 配置出來的常駐 Agent |
| 比喻 | 給你材料，自己蓋房子 | 給你流程，跑在執行時之上 | 蓋好的房子，拎包入住 |
| 誰來用 | 開發者寫程式碼 | 業務人員拖拽 | 業務方配置 Agent、寫 Tool |
| 執行環境 | 自己搭 | 平台提供 | 自帶，裝好就跑 |
| 所在層 | 最底層元件 | 應用層 | 執行時層 |
| 跟 OryxOS 的關係 | 被 OryxOS 復用（做 LLM 呼叫） | 可跑在 OryxOS 之上 | 它自己 |

下面把每一行展開講。

**跟 Dify、Coze 這類工作流編排平台的區別。**

Dify 的產物是一條 workflow，你用拖拽的方式，把 Prompt 節點、HTTP 節點、Code 節點、條件分支拼成一個有向流程，平台負責按這個流程執行。它的核心是"把一個複雜業務流程顯式地編排出來"，適合一次性的、流程明確的任務，使用者主要是業務人員和開發者。

OryxOS 的產物不是 workflow，是一個配置出來的、常駐執行的 Agent，它沒有顯式的流程圖，Agent 在執行時自己根據 prompt、工具和上下文決定下一步做什麼，適合做長期在線的助手。

一句話區別：Dify 編排的是"流程"，OryxOS 承載的是"常駐的 Agent"。兩者不在一層，Dify 完全可以跑在 OryxOS 之上，把 OryxOS 當後端執行時來呼叫。OryxOS 刻意不做可視化編排，正是為了不跟 Dify 搶這一層，而是做它下面那層穩的底座。

**跟 LangChain、LangGraph、langchaingo、Eino 這類框架的區別。**

框架的產物是程式碼，它給開發者一組庫和 SDK，讓你用程式碼把一個 Agent 寫出來，寫完之後部署、運維、擴展、保活都是你自己的事，框架不管執行環境。

OryxOS 的產物是一個裝好就跑的服務，渠道接入、模型路由、記憶、多租戶、審計、Web 管理台這些基礎設施一應俱全，業務方不寫 Agent 後端程式碼，只配置 Agent、寫 Tool。

一句話區別：框架是"給你材料讓你自己蓋房子"，OryxOS 是"蓋好的房子，你拎包入住"。而且兩者是復用關係而非競爭關係，OryxOS 內部的 LLM 呼叫層，正是基於 OpenAI 兼容協議、用 go-openai 這類客戶端薄包裝來實現的。框架解決"怎麼用程式碼呼叫通 LLM 和工具"，OryxOS 解決"怎麼把一堆 Agent 在企業裡可控地常駐跑起來"，分工不同。

把三者收成一張話：框架給你程式碼、要你自己搭執行環境；編排平台給你流程、跑在執行時之上；OryxOS 給你執行時本身，一個讓 Agent 能常駐、可治理、可審計地跑起來的底座。

OryxOS 既復用了框架（拿它當 LLM 呼叫的底層元件），又托住了編排平台（給它當後端執行時），自己專注守在"執行時"這一層。

### 5.6 OryxOS 在安全上怎麼不重蹈 OpenClaw 的覆轍

OpenClaw 的安全問題（第二章講過的 CVE、惡意 skill、憑證收割、第三方 skill 供應鏈風險）不是偶然的 bug，是結構性的。一個開放低門檻的第三方 skill 生態，加上預設寬鬆的權限和較弱的隔離，必然帶來這些問題。OryxOS 既然定位嚴監管企業，安全就必須是 day one 的設計，而不是事後打補丁。具體在幾件事上跟 OpenClaw 走相反的路。

- **Skill 和 Tool 來源受控，不做無約束的公開市場。** OryxOS 不提供"任何人上傳、任何 Agent 隨意拉取"的開放 skill 市場。企業內的 Skill 和 Tool 要經過註冊、審核、簽名、版本管理，來源可追溯。社群的優質 Skill 可以導入，但要經過企業自己的審查關，而不是預設信任。
- **最小權限，而不是預設全開。** 每個 Agent、每個 Tool 拿到的權限是顯式授予的最小集合，檔案系統、網路、shell 的訪問範圍預設收緊，按需放開，而不是 OpenClaw 那種預設能力很大、出事才發現的模式。
- **沙箱隔離是強制的，不是可選的。** Tool 在隔離環境裡執行，有明確的資源和能力邊界，多租戶之間完全隔離，一個租戶、一個 Agent 的越界不會波及其他。
- **憑證不落地，走企業金鑰體系。** API key、token、企業系統的憑證不硬編碼、不明文儲存，對接企業現有的金鑰管理（KMS、Vault 等），憑證的使用全程可審計。
- **prompt injection 和資料外洩要主動防禦。** 借鑒 Hermes 的做法，記憶寫入和工具輸入要經過安全掃描，檢測注入和外洩模式；對 Agent 可以訪問的資料範圍和可以外發的目標做約束。
- **全鏈路審計是底座能力，不是事後補。** 誰、在什麼時候、讓哪個 Agent、呼叫了什麼 Tool、訪問了什麼資料、產生了什麼結果，全程結構化留痕，可以接入企業現有的審計和 SIEM 系統。這正是 OpenClaw 和 Hermes 都缺、而嚴監管企業必須有的東西。
- **走企業現有安全審查流程。** OryxOS 既然是 Go 實現的雲原生服務、跑在企業自己基礎設施上，它就能納入企業現有的程式碼審計、安全掃描、合規過審流程，而不需要像 OpenClaw 那樣靠 Tank OS 這種外部加固鏡像才能勉強上生產。安全不是額外加的一層殼，是從架構裡長出來的。

### 5.7 OryxOS 跟業界其他專案的關係

OryxOS 借鑒了開源 Agent OS 領域已經被驗證的設計哲學。Agent 配置和生命週期、Channel 抽象、三層記憶、Skill 體系（`SKILL.md` 兼容 agentskills.io 開放標準）、Tool 呼叫通過 MCP 協議、單二進制部署這些設計，在 OpenClaw 和 Hermes 上都驗證過能撐住真實場景。OryxOS 把這套設計在 Go 生態裡重新實現，並補齊企業級 Agent OS 必需的多租戶、SSO、RBAC、審計、合規、Web 管理台、深度整合這些能力。

OryxOS 跟 OpenClaw、Hermes 的關係是同類不同定位。三者都是 Agent OS，OpenClaw 偏個人、Hermes 偏個人到小團隊，OryxOS 直接定位嚴監管企業場景。Skill 體系上通過 `SKILL.md` 跟兩者兼容，社群的優質 Skill 經過企業審查後理論上可以導入 OryxOS。這裡不需要論證誰取代誰。開源世界裡同類專案共存是常態，OryxOS 只是把"企業完全可控 + 雲原生原生"這個特定取向做到位。

OryxOS 跟 Dify、Coze 這類編排平台的關係是互補。Dify 做可視化 workflow 編排，OryxOS 做執行時基礎設施，企業可以用 Dify 給業務人員搭快速應用、用 OryxOS 跑核心助手，兩者甚至可以組合（Dify 作應用層，OryxOS 作基礎設施層）。

OryxOS 跟 go-openai、langchaingo、Eino 這些 Go AI 生態的關係是復用。OryxOS 的 LLM Provider 抽象直接基於 OpenAI 兼容協議、用 go-openai 薄包裝實現，不重複造輪子。OryxOS 是 Agent OS，go-openai 是底層 LLM 呼叫能力，兩者在分工上沒有衝突。

## 六、未來方向：從單機到分散式

需要先把當前的邊界講清楚：OryxOS 當前版本做的是單機私有部署。

一個 OryxOS 實例，裝在企業自己的一台伺服器或一個容器裡，跑起一組 Agent，服務一個部門或一個場景。這是刻意的選擇。絕大多數企業落地 Agent 底座，都是從"先在一個場景把它跑通、跑穩"開始的，單機形態最簡單、最易接入、最容易納入現有運維和審計，也最符合"裝一個雲原生服務一樣自然"的初衷。先把單機這件事做扎實，是當前階段的全部重心。

但架構上要為未來留出方向。當一個企業從"一個部門試點"走向"服務全公司"，單機會撞到三件事：

- 扛不住量（單實例的並發和吞吐有上限）
- 扛不住故障（單點掛了整個 Agent 服務就停）
- 扛不住規模化治理（幾十個部門、上百個 Agent、大量租戶共用時，單機的資源和隔離不夠用）。

分散式部署，就是為了應對這三件事而預留的演進方向。這一章講的是設想，不是當前已實現的能力。

講分散式之前要先把一個容易混淆的地方說清楚：這裡其實有兩層完全不同的"分散式"。一層是底座本身的分散式部署，也就是同一個 OryxOS 跑多個副本，解決扛量和高可用，這是運維層面的事，6.1 到 6.4 講的都是它。另一層更遠、也更有意思，是 Agent 之間的分散式協作，多個 Agent 跨節點、跨部門甚至跨組織地互相發現、委託、協同，這裡的"節點"是 Agent 而不是伺服器。後者是一個真正前沿的方向，放在 6.5 單獨講。

### 6.1 演進的核心原則：實例無狀態，狀態外置

從單機走向叢集，最關鍵的一步是把狀態從實例裡剝離出來。單機形態下，session、memory、審計日誌、Agent 配置這些狀態可以放在本地；要做分散式，這些狀態必須外置到獨立的儲存層，讓 OryxOS 實例本身變成無狀態的。任何一個實例掛了或擴容了，不影響整體，因為狀態不在實例裡。

具體設想是：會話和短期上下文外置到 Redis 一類的記憶體儲存，長期記憶和 Skill 庫外置到 PostgreSQL（向量檢索可以用 pgvector 或獨立的向量庫），審計日誌和大檔案外置到對象儲存，Agent 配置和租戶資訊外置到配置中心和資料庫。實例只負責"接訊息、呼叫模型、跑工具、讀寫外置狀態"，自己不持有任何不可重建的狀態。這是分散式的地基，沒有這一步，後面的高可用和水平擴展都無從談起。

### 6.2 多實例下要解決的幾件事

實例無狀態之後，多實例並行會帶來幾個必須解決的協調問題，這裡講清楚思路。

- **渠道接入的訊息不能重複消費。** 多個實例同時連著同一個 Slack 或 Discord 渠道時，一條使用者訊息只能被一個實例處理，不能被多個實例重複回應。設想是通過一個統一的訊息分發層（或基於訊息佇列的消費組）來保證每條訊息恰好被一個實例消費，Gateway 層做無狀態的接入、把訊息投遞到佇列，由實例去搶佔式或分片式消費。
- **Agent 的排程和歸屬。** 多實例下，一個 Agent 的請求可以落到任意實例上（因為狀態外置了，任意實例都能處理），但有些有狀態的長任務、定時任務（cron）需要明確的歸屬，避免重複執行。設想是引入一個輕量的排程協調層，定時任務和長駐任務通過分散式鎖或租約機制保證只有一個實例在跑。
- **多租戶在分散式下的隔離。** 單機的多租戶靠程序內的邏輯隔離，分散式下租戶的資料分散在外置儲存裡，隔離要做到儲存層。每個租戶的 session、memory、審計在儲存層就是隔離的（獨立的 key 前綴、獨立的 schema 或獨立的庫），加上請求鏈路上全程帶租戶標識，保證一個租戶的請求在任何實例上都只能訪問自己的資料。

### 6.3 高可用與水平擴展

有了無狀態實例和外置狀態，高可用和水平擴展就自然了。多實例部署在 K8s 上，前面掛負載均衡，單個實例故障時流量自動切到其他實例，狀態不丟（因為在外置儲存裡）。負載上來時，水平擴容實例數即可，因為實例無狀態，擴容不需要資料遷移。外置的儲存層（Redis、PG、對象儲存）各自按成熟的方案做自己的高可用，這些都是企業已經熟悉的中間件。

### 6.4 為什麼 Go 做分散式更本命

這一章其實是"雲原生原生"價值的又一次體現。分散式系統要解決的 leader 選舉、服務發現、配置管理、水平擴容、負載均衡這些問題，其成熟方案幾乎清一色是 Go 寫的，而且大概率就是企業現有雲原生體系裡已經在用的：leader 選舉和一致性儲存用 etcd，水平擴容和自愈靠 K8s 的 HPA 與無狀態副本調度，服務間異步通信用 NATS，同步 RPC 用 gRPC，而連服務網格 Istio、Linkerd 也都是 Go。OryxOS 做分散式，不需要自己造這些輪子，直接站在這套用 Go 寫成的雲原生分散式基礎設施上，跟企業現有的 K8s 平台用同一套工具、同一套運維方法。

而且這裡有一層別的語言沒有的順：這些分散式底座本身就是 Go 寫的，OryxOS 用 Go 去對接它們——無論是嵌入 etcd 的客戶端做選舉、寫 K8s Operator、還是直接連 NATS / gRPC——用的都是母語的一等庫，沒有跨語言綁定的接縫。這正是 Node.js 的 OpenClaw 和 Python 的 Hermes 做企業級分散式時要費很大勁、而 Go 順手就能做的地方。分散式、高可用、服務治理，本來就是雲原生生態最成熟的強項，而這套生態的母語就是 Go。把 Agent OS 放在這套地基上，分散式不是從零搭，是復用。

需要再強調一次：以上是面向規模化的演進設想，當前版本聚焦把單機做扎實。把分散式的方向想清楚、在架構上預留好，是為了讓單機版本的設計不堵死未來的路，而不是現在就把複雜度全壓上來。

### 6.5 更遠的願景：分散式 Agent 協作

前面 6.1 到 6.4 講的是"一個 OryxOS 跑多份副本"，那是把同一個底座做大。還有一個更遠、也更有意思的方向，是把"分散式"用在 Agent 身上，而不是用在底座的副本上。

設想這樣一個場景：一個企業裡有幾十上百個 Agent，分散在不同部門、不同機器，甚至延伸到合作夥伴的組織裡。運維部門有運維 Agent，財務有財務 Agent，法務有法務 Agent。一個真實的業務往往橫跨多個部門，比如一筆大額採購，要運維 Agent 確認資源、財務 Agent 核算預算、法務 Agent 審合同。

今天這些 Agent 是一個個孤島，各跑各的。而分散式 Agent 協作要解決的，就是讓它們能跨節點地互相發現、把任務可靠地委託給對方、共享必要的上下文、協同完成一件橫跨多方的事。這裡的"節點"是 Agent，整個圖景更像一個 Agent 版的分散式系統。

這件事現在還很早。業界關於 multi-agent 的探索，大多還停留在單機程序內的幾個 Agent 互相 delegate，真正跨節點、跨組織的 Agent 協作，基礎設施幾乎還是空白。這跟分散式系統的早期很像。先有單機多程序，後來才有跨機器的服務發現、RPC、訊息中間件把它們連起來。

Agent 世界現在大概就在"單機多程序"這個階段，而把多個節點的 Agent 可靠連起來的那層中間件，還沒真正立起來。所以這是一個方向性的、卡位性的願景，不是當下的需求。市場連"單個 Agent 穩定上生產"都還沒普遍做到，談跨節點 Agent 協作的真實需求為時尚早。把它寫進來，是因為它是 OryxOS 這條線自然會生長到的遠方，值得現在就看清。

而這個遠方有一個關鍵的技術地基，恰好不在 OryxOS 自己身上，而在 Agent 之間的通信底座上。多個 Agent 要跨節點可靠協作，最難的不是單個 Agent 跑得好不好，而是它們之間怎麼註冊發現、怎麼可靠地異步通信、怎麼在不可靠的網路上保證訊息不丟不重、怎麼傳遞跨節點的上下文，這些正是訊息和通信基礎設施要解決的問題。而這層通信底座要接的 NATS、gRPC 這類訊息與 RPC 中間件，本身也都是 Go 寫的，OryxOS 用 Go 去承載它、把跨節點的 Agent 連起來，接得更自然。

沿著這個思路，OryxOS 的遠期圖景可以這樣描述：OryxOS 是單個節點上的 Agent 執行時，而連接多個 OryxOS 節點、讓上面的 Agent 能跨節點可靠協作的，是一層專門的 Agent 通信底座。 單節點的執行時和跨節點的通信底座是兩件事，分開演進，最後合起來，才構成完整的"分散式 Agent OS"。

需要清楚地標註邊界：6.5 是這份調研裡最遠的一筆，是願景層面的設想，跟當前要做的單機版本隔著好幾步。寫下它，是為了讓方向感完整。OryxOS 當前扎扎實實做單機，中期沿 6.1 到 6.4 演進到底座的分散式部署，遠期才走向分散式 Agent 協作。每一步都建立在前一步做扎實的基礎上，不跳步。

三個階段並排看，路標就清楚了。

| 階段 | 形態 | 解決什麼 | 狀態 |
| --- | --- | --- | --- |
| 當前 | 單機私有部署 | 一個場景先跑通、跑穩，易接入、易審計 | 當前重心 |
| 中期 | 底座分散式部署 | 扛量、高可用、規模化治理（多副本無狀態） | 架構預留 |
| 遠期 | 分散式 Agent 協作 | 跨節點 Agent 互相發現、委託、協同 | 願景 |

## 附錄 A：關鍵術語

- **Agent OS**：Agent Operating System，執行和管理 AI Agent 的基礎設施層，裝在使用者（或企業）自己的機器上，提供多渠道、多 LLM 路由、記憶、工具、隔離等完整執行環境。
- **Agent**：具象的智能體，有具體的工種、人格設定和任務範圍。一個 Agent 由 prompt、Skills、Tools、Memory 幾部分組合而成，在 Agent OS 上配置出來，不是寫程式碼寫出來的。
- **Skill**：可復用的 Agent 能力模板，用 `SKILL.md` 檔案格式描述，兼容 agentskills.io 開放標準。OpenClaw 和 Hermes 都用這個格式。
- **Tool**：Agent 可以呼叫的外部能力，通常通過 MCP 協議暴露。業務方用任何語言寫 Tool，註冊到 Agent OS 供 Agent 使用。
- **Channel**：Agent 對外接入的訊息渠道，包括 Slack、Telegram、Discord、郵件等。（註：OryxOS 專屬術語中 HTTP API／Web 歸 Web Service，不算 Channel；見需求文檔術語定義）
- **LLM Provider**：大模型的提供方抽象，實現統一介面讓 Agent 不感知具體呼叫的是哪家模型。
- **MCP**：Model Context Protocol，Anthropic 2024 年 11 月提出的 LLM 與外部工具或資料源連接的開放協議，目前是 Agent 生態的事實標準。
- **Agent 編排平台**：visual workflow builder，用拖拽方式組合節點搭 AI 應用。Dify、Coze、扣子是代表。跟 Agent OS 是不同層級，Agent OS 是底層執行時，編排平台是上層應用工具。
- **Agent 框架**：給開發者用程式碼寫 Agent 的庫或 SDK。LangChain、langchaingo、Eino 是代表。框架的產物是程式碼，執行需要開發者自己搞定。
- **多租戶**：一個 Agent OS 實例同時服務多個組織、部門、專案，每個租戶獨立 memory、session、data，完全隔離。
- **Gateway**：Agent OS 裡負責連接外部渠道（IM、郵件等）和路由訊息的核心元件。OpenClaw 和 Hermes 都用這個術語。
- **go-openai**：Go 社群維護的 OpenAI 兼容協議客戶端，是 Go 接 LLM 事實上的標準客戶端。OryxOS 的 LLM Provider 抽象基於它做薄包裝，接 OpenAI 兼容協議。
- **官方 Go MCP SDK**：Model Context Protocol 的官方 Go 實作，加上社群成熟實作（如 mark3labs/mcp-go），是 Go 生態接入 Tool 的一等公民。
- **cobra**：Go 的命令行框架，kubectl、docker、gh 等同款，OryxOS 的 CLI 基於它構建。
