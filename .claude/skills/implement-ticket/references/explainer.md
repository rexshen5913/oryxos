# 開發解釋 Artifact

實作收尾時產出的一份可讀文檔，記錄**這次是怎麼想的**——不是結論清單，是推導過程。

## 檔名與 URL

**同一個檔案路徑重新發布會覆蓋同一個 URL。** 檔名寫死的話，下一張票會把上一張蓋掉。

檔名一律帶 ticket 編號，寫在 scratchpad：

```
<scratchpad>/ticket-47-52-<主題>.html
<scratchpad>/ticket-54-<主題>.html
```

同一張票要改內容時，用**同一個路徑**重新發布（保住原 URL）；不同票用新路徑。

## 命名

`<title>` 是 gallery 與瀏覽器分頁上的名字：

- **是名字，不是說明。** 兩到四字的名詞片語，對這次的主題有辨識度
- **不帶解釋性後綴。** 不要「事件流落地軌跡 — ticket #47 的完整思路」這種破折號拼接
- 不用票號當標題（票號進 description）

`description` 是 gallery 卡片的副標，**票號寫這裡**——清單長了要靠它找：

```
ticket #47 + #52 · 從讀上下文到通過審查的完整思路
```

`favicon` 一到兩個 emoji，選跟主題有關的；同一張票重發時**不要換**。

## 內容結構

十段。小票可以合併，但順序不變——它就是實際的工作順序。

| 段 | 內容 | 關鍵 |
|---|---|---|
| 00 | 定位 | 這張票在整個專案的哪個位置、為什麼是現在做 |
| 01 | 讀上下文 | 那張約束表（來源／約束／對這次的實際影響） |
| 02 | 票之間的關係 | 為什麼一起做、或為什麼可以單獨做 |
| 03 | 型別與介面 | 抄了哪個既有形狀、三個共同點各自的理由 |
| 04 | TDD 紅燈 | 第一支測試，以及它為什麼這樣斷言 |
| 05 | 第一階段 | 行為零變更的 diff ＋ 中間那次驗收的輸出 |
| 06 | 關鍵推導 | **最重要的一段**，見下方 |
| 07 | 主要實作 | 每個「位置選擇」的理由 |
| 08 | 難題 | 卡住的那件事、三條路各自的問題、採用哪條 |
| 09 | 自我審查 | 突變表，挑幾格說明各自在守什麼 |
| 10 | 外部審查 | Codex 抓到什麼、怎麼修、學到什麼 |
| — | 收尾 | 貫穿全程的判準（不是這次的結論，是可帶走的判斷方式） |

### 第 06 段的寫法

挑**一個實際發生過的推導**，把過程完整寫出來：

1. spec 或 ticket 字面上說什麼
2. 哪一條 AC／術語定義跟它對不上
3. 去追什麼（貼**真的去讀的那段既有程式碼**）
4. 追出什麼
5. 結論，以及它跟字面說法的差異

這一段是整份文檔的價值所在。**結論任何人都寫得出來，推導不行。**

## 寫法原則

- **貼真的程式碼**，從最終檔案取，不是憑記憶重寫
- **每段程式碼要說「功能是什麼」和「為什麼這樣寫」**，不逐行翻譯語法
- **承認錯的地方。** 第 10 段要寫審查抓到什麼、原本錯在哪。修完就沒事了不是重點，「當時為什麼會那樣寫」才是
- 術語一律用 `CONTEXT.md` 的正式詞，不漂移到 `_Avoid_` 那欄
- 讀者是**正在學這套流程的人**，不是已經知道結論的人

## 設計規格

視覺跨票保持一致——多份文檔應該看起來像同一個系列。**除非使用者另有要求，照這份 token 走。**

### 色

```
--ground: #FBFCFD    極淺、帶一點藍偏（不是純白）
--surface: #F1F4F7   卡片、表格底
--ink: #16212B       帶藍的深墨
--muted: #5D6D7C     藍灰
--line: #D5DEE5      分隔線
--accent: #0B6E6E    深青（序號、連結、關鍵標記）
--warn: #B4530A      燒橙，**只給審查抓到的問題**，不當第二個 accent
--code-bg: #131C23   程式碼底（兩個主題都用深色）
```

深色主題把 ground 換 `#0E1519`、ink 換 `#DFE7EC`、accent 提亮成 `#4FBDB6`。

**三態都要處理**：bare `:root` 定義完整淺色；`@media (prefers-color-scheme: dark)` 加 `:root:not([data-theme="light"])` 守衛；`:root[data-theme="dark"]` 再定義一次。任何顏色都不可以只定義在 media 或 `[data-theme]` 區塊裡。`body` 要有明確的 `background`。

### 字

```html
<link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=Newsreader:ital,opsz,wght@0,6..72,400;0,6..72,500;0,6..72,600;1,6..72,400&family=IBM+Plex+Mono:wght@400;500;600&family=IBM+Plex+Sans:wght@400;500;600&display=swap">
```

- **Newsreader** — 標題。有文獻感，適合帶敘事的技術文
- **IBM Plex Sans** — 內文。為技術文檔而生
- **IBM Plex Mono** — 程式碼、標籤、數字。與內文同家族

中文 fallback：`"Noto Sans TC"`、`"Songti TC"`。

### 版

- 單欄。散文 `68ch`，程式碼與表格放寬到 `82ch`——文字窄、程式碼寬形成節奏
- **左側編號軌**：`00`–`10` 的圓形序號 ＋ 連接線。這是真的序列，編號在這裡是資訊不是裝飾
- 程式碼區塊：深底、圓角、帶 `figcaption` 標檔名 ＋ 右側一個短標籤（`既有` / `新增` / `Red` / `第一階段`）
- 表格包在 `overflow-x: auto` 容器裡，頁面本身不橫向捲動
- `font-variant-numeric: tabular-nums` 給所有對齊的數字

### 元件

固定幾種，跨票重複用：

- **callout** — 左側 2px accent 邊，引 spec／ticket 原文或點出關鍵判斷；`.warn` 變體（燒橙）給審查意見
- **paths** — 決策對照。每條一列，`路徑 A` / `路徑 B` / `採用`，採用那條用 accent 底
- **seq** — 事件或步驟序列，小方塊 ＋ 箭頭
- **principles** — 收尾的判準列表，`01`–`05` 前導零編號

### 語法上色

程式碼用 `<span>` 手工標，四個 class 就夠：

```
.c   註解（斜體、低對比）
.k   關鍵字
.s   字串
.hl  本次的重點行（提亮、加粗）
```

`.hl` 很重要——它讓讀者一眼看到「這次加了什麼」。

**記得 escape**：`<` → `&lt;`、`>` → `&gt;`、`&` → `&amp;`。Go 常見的 `>=`、`<-ctx.Done()`、`&Struct{}` 都會踩到。
